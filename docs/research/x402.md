## Wire format: v2 versus requested legacy headers

| Item | Protocol v1 | Protocol v2 |
|---|---|---|
| 402 challenge | JSON response body | Base64 JSON in `PAYMENT-REQUIRED` response header |
| Signed payment request | `X-PAYMENT` | `PAYMENT-SIGNATURE` |
| Settlement response | `X-PAYMENT-RESPONSE` | `PAYMENT-RESPONSE` |
| Network | `base-sepolia` | `eip155:84532` |
| Atomic price field | `maxAmountRequired` | `amount` |
| Resource metadata | Inside each requirement | Separate `resource` object |

All payment/receipt headers above contain **standard Base64 of UTF-8 JSON**, not a JWT, hex string, or `Bearer ...`. Header names are case-insensitive. The installed Python middleware returned **HTTP 402 with body `{}`**; do not assume `response.json().accepts` in v2. The header decoded to this shape:

```json
{
  "x402Version": 2,
  "error": "Payment required",
  "resource": {"url": "https://api.example.com/paid", "description": "test", "mimeType": "application/json"},
  "accepts": [{
    "scheme": "exact", "network": "eip155:84532",
    "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
    "amount": "1000", "payTo": "0x1111111111111111111111111111111111111111",
    "maxTimeoutSeconds": 300, "extra": {"name": "USDC", "version": "2"}
  }]
}
```

V2 `PaymentRequirements` fields: `scheme`, `network`, `asset`, `amount`, `payTo`, `maxTimeoutSeconds`, `extra` (SDK defaults to `{}`). `PaymentRequired` additionally supports optional `extensions`. Python uses snake_case constructor arguments and serializes to camelCase (`model_dump(by_alias=True, exclude_none=True)`).

The decoded v2 payment is `{x402Version:2, accepted:<chosen requirements>, payload:{signature,authorization}, resource?:..., extensions?:...}`. EIP-3009 `authorization` contains `from`, `to`, `value`, `validAfter`, `validBefore`, `nonce`; integer values/timestamps are decimal strings and nonce is a random 32-byte `0x` hex value. `to`/`value` must match the server's requirements.

For legacy clients, the 402 JSON is `{x402Version:1,error?:string,accepts:[...]}`. Each v1 requirement contains `scheme`, `network`, `maxAmountRequired`, `resource`, `description`, `mimeType`, optional `outputSchema`, `payTo`, `maxTimeoutSeconds`, `asset`, optional `extra`. `X-PAYMENT` decodes to `{x402Version:1,scheme:"exact",network:"base-sepolia",payload:{signature,authorization}}`. `X-PAYMENT-RESPONSE` decodes to a settlement result; legacy wire fields include `success`, `errorReason`, `transaction`, `network`, and `payer`. Do not mix v1 envelopes with v2 headers.

Sources: [v2 specification](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md), [Python wire models](https://github.com/x402-foundation/x402/tree/main/python/x402/x402/schemas), [HTTP transport specification](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md).

## Base Sepolia USDC and facilitator

- Chain ID **84532**, CAIP-2 **`eip155:84532`**; USDC **`0x036CbD53842c5426634e7929541eC2318f3dCF7e`**, **6 decimals**. `$0.001` = `"1000"` atomic units; `$1` = `"1000000"`.
- `exact` with this USDC uses EIP-3009 authorization signed as EIP-712 (`TransferWithAuthorization`, domain `name:"USDC"`, `version:"2"`, chainId 84532, verifyingContract=USDC). Facilitator submits settlement and pays gas. The payer needs test USDC; ordinary EOA EIP-3009 payment signing does not require payer ETH or a token approval transaction.
- Test facilitator: **`https://x402.org/facilitator`**, no API key. A live GET to `/supported` returned HTTP 200 and advertised v2 `exact` on `eip155:84532` and legacy v1 `base-sepolia`.
- CDP base URL: **`https://api.cdp.coinbase.com/platform/v2/x402`** — **no trailing `/facilitator`**. Supports Base Sepolia and mainnet; requires CDP request-specific Bearer JWT authentication generated using `CDP_API_KEY_ID` / `CDP_API_KEY_SECRET`. Those credentials are not themselves Bearer tokens. CDP's `cdp.x402` helper can configure this; its package version was not installed/verified in this experiment.
- Public x402.org facilitator is for testnet, not mainnet. Call `GET <base>/supported` before configuring a scheme/network.

Both **`POST <base>/verify`** and **`POST <base>/settle`** take `Content-Type: application/json` and the same envelope:

```python
body = {
    "x402Version": 2,
    "paymentPayload": decoded_payment,       # JSON object, not the Base64 header
    "paymentRequirements": server_requirement,  # server-owned selected requirement
}
# await httpx_client.post(base + "/verify", json=body, headers=auth_headers)
# await httpx_client.post(base + "/settle", json=body, headers=auth_headers)
```

`verify` returns `{isValid:boolean, invalidReason?:string, invalidMessage?:string, payer?:string}`. `settle` returns `{success:boolean, transaction:string, network:string, payer?:string, errorReason?:string, errorMessage?:string, amount?:string}`; extensions/extra may also be present. HTTP 200 alone does not establish payment. Verification does not move funds or guarantee later settlement; release paid results only after successful settlement. `PAYMENT-RESPONSE` carries the Base64 settlement JSON. Do not submit settlement blindly again after an ambiguous timeout: reconcile the transaction/nonce first.

Sources: [EVM exact scheme](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_evm.md), [default assets](https://github.com/x402-foundation/x402/blob/main/DEFAULT_ASSETS.md), [Circle USDC addresses](https://developers.circle.com/stablecoins/usdc-contract-addresses), [CDP facilitator](https://docs.cdp.coinbase.com/x402/seller/facilitator), [verify REST](https://docs.cdp.coinbase.com/api-reference/v2/rest-api/x402-facilitator/verify-payment), [settle REST](https://docs.cdp.coinbase.com/api-reference/v2/rest-api/x402-facilitator/settle-payment).

## FastAPI server: exact imports and runnable setup

```python
# server.py
import os
from fastapi import FastAPI
from x402 import x402ResourceServer
from x402.http import HTTPFacilitatorClient, FacilitatorConfig, PaymentOption, RouteConfig
from x402.http.middleware.fastapi import PaymentMiddlewareASGI
from x402.mechanisms.evm.exact import ExactEvmServerScheme

network = "eip155:84532"
facilitator = HTTPFacilitatorClient(FacilitatorConfig(
    url=os.getenv("FACILITATOR_URL", "https://x402.org/facilitator")
))
server = x402ResourceServer(facilitator).register(network, ExactEvmServerScheme())
app = FastAPI()
app.add_middleware(PaymentMiddlewareASGI, server=server, routes={
    "GET /paid": RouteConfig(
        accepts=[PaymentOption(scheme="exact", network=network,
            pay_to=os.environ["PAY_TO"], price="$0.001", max_timeout_seconds=300)],
        description="Paid test resource", mime_type="application/json",
    )
})

@app.get("/paid")
def paid():
    return {"ok": True}
# Run: python -m uvicorn server:app --host 0.0.0.0 --port 8000
```

Verified constructors: `PaymentMiddlewareASGI(app, routes, server, paywall_config=None, paywall_provider=None)`; `HTTPFacilitatorClient(config=None)`; `FacilitatorConfig(url=..., timeout=90.0, http_client=None, auth_provider=None, identifier=None)`; `ExactEvmServerScheme()` is the server alias, not the signer-taking client class. Server initialization fetches facilitator capabilities; an unavailable facilitator can block the first paid request. [Python README](https://github.com/x402-foundation/x402/blob/main/python/x402/README.md), [seller guide](https://docs.x402.org/getting-started/quickstart-for-sellers).

## JavaScript clients

Server private key, ESM/TypeScript:

```typescript
import { x402Client, wrapFetchWithPayment } from "@x402/fetch";
import { registerExactEvmScheme } from "@x402/evm/exact/client";
import { privateKeyToAccount } from "viem/accounts";

const signer = privateKeyToAccount(process.env.EVM_PRIVATE_KEY as `0x${string}`);
const client = new x402Client();
registerExactEvmScheme(client, { signer, networks: ["eip155:84532"] });
const paidFetch = wrapFetchWithPayment(fetch, client);
const response = await paidFetch("http://localhost:8000/paid");
console.log(response.status, await response.json());
```

Browser wallet: construct the same payment client using an injected EIP-1193 provider. Execute after a user gesture; this requests account access and a typed-data signature. Private keys stay in the wallet.

```typescript
import { createWalletClient, custom, type EIP1193Provider } from "viem";
import { baseSepolia } from "viem/chains";
import type { ClientEvmSigner } from "@x402/evm";
import { x402Client, wrapFetchWithPayment } from "@x402/fetch";
import { registerExactEvmScheme } from "@x402/evm/exact/client";

export async function walletFetch(provider: EIP1193Provider) {
  const wallet = createWalletClient({ chain: baseSepolia, transport: custom(provider) });
  const [address] = await wallet.requestAddresses();
  if (!address) throw new Error("No wallet account");
  await wallet.switchChain({ id: baseSepolia.id });
  const signer: ClientEvmSigner = {
    address,
    signTypedData: args => wallet.signTypedData({ ...args, account: address }),
  };
  const client = new x402Client();
  registerExactEvmScheme(client, { signer, networks: ["eip155:84532"] });
  return wrapFetchWithPayment(fetch, client);
}
```

`wrapFetchWithPayment(fetch, client)` returns a fetch-compatible async function. Axios equivalent: `import { wrapAxiosWithPayment } from "@x402/axios"; const api = wrapAxiosWithPayment(axios.create(), client);`. Supply an imported `axios` instance. The browser snippet passed TypeScript 7.0.2 with `tsc --noEmit --skipLibCheck --target ES2022 --module NodeNext --moduleResolution NodeNext browser.ts`. Browser wallet interaction was not exercised; ESM imports, local account signing, header encoding and fetch retry were.

- For cross-origin browser requests, allow `PAYMENT-SIGNATURE` (and `X-PAYMENT` only if supporting v1), allow `OPTIONS`, and expose `PAYMENT-REQUIRED` / `PAYMENT-RESPONSE` in CORS. Put CORS outside the payment middleware. Wallet refusal should surface as a cancelled purchase.
- The wrapper can sign a payment automatically after 402. Apply an amount/asset/payee policy before using it on arbitrary URLs; show the quoted price before a browser purchase. Use a fresh payment nonce for each purchase.
- Default middleware verifies before the route and settles after a successful route response. A handler's irreversible side effects may happen before settlement: implement idempotent job acceptance/accounting rather than treating handler entry as proof of completed payment.
- `FACILITATOR_URL`, `PAY_TO`, and `EVM_PRIVATE_KEY` are example application variables, not automatically read by x402. Never put a server private key in a `NEXT_PUBLIC_*` variable.

Sources: [fetch SDK](https://github.com/x402-foundation/x402/tree/main/typescript/packages/http/fetch), [EVM SDK](https://github.com/x402-foundation/x402/tree/main/typescript/packages/mechanisms/evm), [buyer guide](https://docs.x402.org/getting-started/quickstart-for-buyers).

## Testnet prerequisites and no-funds simulation

Full settlement needs a receiving address, a payer wallet with **Base Sepolia test USDC**, a reachable facilitator, and a running API. Obtain test USDC from [Circle's faucet](https://faucet.circle.com/). A self-hosted facilitator additionally needs Base Sepolia ETH for gas and an RPC connection. With the hosted EIP-3009 facilitator, the payer need not hold ETH. Testnet assets have no real monetary value; an empty wallet cannot complete a real payment.

For deterministic HTTP tests, replace the facilitator object in the server above with this local fake. **Never deploy it: it accepts any payload and does not transfer funds.**

```python
from x402.schemas import SupportedResponse, SupportedKind, VerifyResponse, SettleResponse

class FakeFacilitator:
    def get_supported(self):
        return SupportedResponse(kinds=[SupportedKind(
            x402_version=2, scheme="exact", network="eip155:84532")])
    async def verify(self, payload, requirements):
        return VerifyResponse(is_valid=True,
            payer=payload.payload["authorization"]["from"])
    async def settle(self, payload, requirements):
        return SettleResponse(success=True, transaction="0x" + "0" * 64,
            network="eip155:84532", payer=payload.payload["authorization"]["from"])

```

Actual experiment, Windows Node 24.15.0 / Python 3.13.7 under `%TEMP%`:

1. FastAPI `TestClient` returned `402 {}`; decoded `PAYMENT-REQUIRED` contained `amount:"1000"` and the correct test USDC address.
2. JS `generatePrivateKey()` / `privateKeyToAccount()` created an ephemeral unfunded account. `wrapFetchWithPayment` made exactly two mock-fetch calls, producing a `PAYMENT-SIGNATURE` header.
3. `viem.verifyTypedData` validated the signature using domain `USDC/2/84532/<USDC>` and `authorizationTypes` from `@x402/evm`; returned **true**.
4. Sent that header to Python `TestClient` using `FakeFacilitator`: **200 `{"ok":true}`**, with a decoded `PAYMENT-RESPONSE` containing `success:true`, payer, zero mock transaction hash, and `eip155:84532`.
5. Live `/supported` discovery passed. The exact documented FastAPI server, with the real test facilitator, also returned **402 `{}` with `payment-required` present**. **No real `/settle` call, token transfer, browser wallet approval, or authenticated CDP call was performed.**
