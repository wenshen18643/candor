## Reviewed and judged safe within the tested boundaries

- Reviewer report, file, status, analysis, job, SSE, message, custody, and admin retry routes enforce organisation membership. Added `test_reviewer_routes_reject_foreign_organisation` exercises the route matrix. Campaign recipients are the organisation's reviewers under this schema; submission validates the exact recipient set and threshold. Admin payment summaries deliberately expose only amounts/statuses as specified.
- Inbox JWT purpose, signed public key, and report-ID scope are checked on reads and writes. Reviewer and inbox challenges use distinct exact protocol strings, single-use state, and expiry. JWT decoding pins HS256, issuer, audience, and required expiry/issued-at claims; reviewer role and organisation are checked against current records.
- Custody verifies Ed25519 over the exact request/report/requester message. Self-approval, duplicate approvers, missing custody shares, wrong organisations, and expired pending requests fail. `test_quorum_rejects_duplicate_wrong_context_and_expired_approval` adds a three-share quorum and a signature with an extra newline to existing coverage. Resealed-share bytes are not included in the signature because the protocol explicitly specifies only the identifiers.
- Blind-token signature verification uses RSA-PSS/SHA-384 with the required salt length and campaign issuer. Token spending and identity quotas are transactional, with uniqueness constraints and concurrency tests. Identity preserves no proof, raw nullifier, or blinded-message records; issuer encryption authenticates campaign context. Issuance rechecks quota, expiry, and epoch after asynchronous signing work.
- x402 requires fixed scheme/network, quoted recipient and amount, facilitator verification and successful settlement. The configured asset/domain is sent as server-owned requirements to the facilitator. Nonces are payer-scoped and unique; idempotency is organisation-scoped and existing jobs are report-bound. Ambiguous settlements remain blocked for reconciliation. Existing tests cover concurrent payment replay, separate database records, invalid verification, and timeout recovery. Real signature, asset/domain, and validity-window enforcement is delegated to the facilitator; no funded settlement was performed here.
- Blob references accept only SHA-256 hex and verify content hashes. SQL uses bound expressions/prepared statements. API streaming request sizes and identity body sizes are bounded. The adversarial deeply nested API JSON request already returned a sanitized 422, so no parser change was made (`test_deep_json_is_rejected_without_echo`). CORS uses the configured web origin without credentialed wildcards. Error handlers and application loggers do not echo bodies, IPs, tokens, keys, or provider exceptions. Production already rejected mock payments, demo-key endpoints, and development authentication secrets.
- Merkle inclusion/consistency vectors, signed-head verification, audit outbox recovery, encrypted inbox recipient filtering, deterministic mock adapters, and persistent identity quota/restart tests continue to pass.

## Operational changes and limits

**Worker integration is required before end-to-end analysis can run with this API.** The current `services/pipeline/src/candor_pipeline/worker.py` does not send `X-Job-Attempt`. Its events, complete, and fail requests must send the `attempt` returned by claim. Those files were explicitly out of scope and were not changed. Missing/stale attempts now fail closed with 409. Claim still requires only the worker token.

API startup creates the additive `message_order` and `message_reads` tables. It backfills existing message order by original creation time and ID, without changing ciphertext. Backfill is idempotent (`test_restart_backfills_legacy_message_order_once`). Legacy messages may appear unread until reopened. New inbox challenge subjects use the HMAC scheme; an old in-flight challenge must be requested again. Existing committed payment jobs remain replayable; orphaned settlements created by older job-ID derivation may require operator reconciliation.

Identity limits are per process: 60 requests per socket peer with one token/second refill; 600 globally with ten/second refill; 16 in flight; at most 10,000 peer entries. A proxy is treated as the peer unless deployment provides a separately trusted client-address policy. Multi-process deployments need corresponding ingress limits. SSE bounds are likewise per application instance.

Hour bucketing applies to new application records. It cannot erase previously published precise signed heads, historical records, filesystem/WAL metadata, external access logs, public-chain block times, or timing observed by actively polling a live service. It does not guarantee anonymity for a lone report/payment in an hour. Identity's prescribed short-lived session expiry and authentication expiry remain precise to enforce their 15-minute/120-second TTLs; these are not shared reporter identifiers across identity and reports. Protect operational storage and avoid retaining proxy/client logs. The inbox HMAC protects a database-only disclosure, not a compromise that also obtains the API secret.

The protocol's fixed issuer key and token format do not authenticate token epochs. Issuance enforces epoch quotas, but independently expiring redeemed tokens requires a coordinated protocol/client change outside this review. No live PostgreSQL server, funded x402 transfer, EVM anchor, or mobile Self proof was exercised. No plaintext evidence was needed for this review.
